## Native resident-input method

- Feed a fixed 96-frame, 298,598,400-byte synthetic NV12 fixture. A frame has 1920 × 1080 visible pixels, two 8-bit NV12 planes and 3,110,400 bytes on disk. The stored D3D11 surface is aligned to 1920 × 1088. The exact fixture hash is in the metadata. The original fixture is withheld from this release.
- Select the B580 hardware implementation and allocate video-memory input surfaces through D3D11 on Windows or VA-API on Linux. Upload and read back the surfaces before timing. Recycle verified input surfaces with no timed CPU input uploads. This reproducer omits decoding, resizing and tone mapping. A media driver's internal allocation placement is outside the public input-mode query.
- Request HEVC Main, nominal 24/1 fps, target usage 4, low-power hardware encode, async depth 3, GOP size 248, reference distance 8 and four reference frames. The timed cases run uncapped. Compare ICQ quality 23 with CQP I/P/B values 23/23/23 and query the effective parameters. Those values select different rate-control algorithms and yield different quality, bitrates and bitstreams.
- Count completed encoded frames, using deltas divided by actual monotonic time deltas in windows relative to the first completed output. Record startup separately. A finite run qualifies only after the requested frame count and natural-EOF software decode agree. For the validated native timed runs, decode every frame to natural EOF and compare ordinal-aligned decoded pixels with the periodic source, recording per-frame PSNR. The results measure throughput and basic correctness on this fixture. They are not expected FPS for a 4K HDR end-to-end transcode.
- Capture actual resource geometry and software versions with the results. The native Linux client requests VRAM allocations and verifies upload/readback and allocator counters. Its placement instrumentation records requested allocation policy. It does not measure the residency of every internal media allocation.

The fixture was generated by the following FFmpeg command. The recorded generator executable hash and expected output hash are in the metadata. Builds can differ, so verify the result before treating a new input as byte-identical.

```sh
ffmpeg -hide_banner -nostdin -loglevel error -f lavfi \
  -i testsrc2=size=1920x1080:rate=24 -frames:v 96 -threads 1 \
  -pix_fmt nv12 -f rawvideo testsrc2-1080-nv12.yuv
```

### Mechanism tests and limits

| Discriminator | Observation | Bound on the inference |
| --- | --- | --- |
| Reboot and driver changes | Early manual 9150 → 9033 → 8974 sequence showed the same class of slowdown. Rebooted 8974 and verified 8993 both reproduced it in matched tests. | Early package comparisons had weaker controls. The 8993 change was unrebooted and supporting components remained mixed. |
| Input memory and storage | A matched 90-second comparison raised the late floor from about 20.7 fps for system input to 32.8 fps for real D3D11 video input. T269 found 27 completed video-input logs with zero external input locks and no reported input-mode change. The RAM-output image reproduced the slow path. | An application-level switch to system inputs was not seen. Internal copies, resource eviction and placement changes remain possible. QSVEnc's `--disable-d3d` requests system-memory input from the start and therefore cannot establish an automatic fallback. |
| Load and power | A separate compute test sustained high core clocks and substantial board power. The observed encode slowdown remained under a temporary enforced clock floor. A 1 → 2 → 1 encoder experiment improved the primary in the concurrent phase, with about 36.8 fps total throughput in the selected late window. | The observations weaken a simple GPU-wide clock cap or an idle-detection explanation. They do not qualify private media clocks, voltage policy or scheduling. |
| Time versus submitted work | After a 30.007 s post-Init hold with zero accepted or completed frames, the first-five-second rate was 508.57 fps and the late rate 34.02 fps. The immediate control gave 511.22 and 32.81 fps. | Waiting without work did not consume the initial burst. Cumulative submissions, elapsed processing and resource pressure remain coupled. |
| CPU and NUMA | Restricting the process to the GPU-local node did not restore performance. A selected VidMm worker ran mainly on the remote node in both phases. | A local-to-remote worker migration did not explain those selected intervals. Internal page placement and NUMA costs were not fully controlled. |
| Rate control | HEVC CBR and VBR reached 33.65 and 33.83 fps at 15–30 s. HEVC CQP delivered 180.07 fps at 240–300 s in a paced 180 fps run with 54,000 validated frames. | The slow state is broader than the one ICQ setting. The five-minute run was paced and cannot establish uncapped five-minute capacity. |
| Per-picture QP workaround | A native HEVC CQP prototype applied QP23 and alternating QP23/29 at 632.70 and 638.35 late fps. All 75,009 frames validated. Slice base QP matched each request. | This qualifies externally supplied QP control. No adaptive quality policy, ICQ or CRF equivalence, or FastFlix/Plex integration was demonstrated. |
| Public WDDM traces | Owned copy contexts queued behind matching kernel fences. Selected waits reached 109 ms. The VidMm worker stack showed evict/make-nonresident and GPU VA/TLB flush dependencies. In the bounded T249 analysis, matched small-allocation evictions rose from 0.036 to 13.623 per completed output in early versus 30–45 s windows. | T247 lacked usable early trace coverage. T249 exceeded the trace budget, and there was no matched fast-CQP trace with the same instrumentation. These events localise slow-state work without attributing the initiating fault. |

The evidence therefore supports a Windows media/graphics-stack interaction under this platform's small aperture as an investigation lead. It leaves open which layer initiates the work, whether Windows large BAR would remove it, and which features matter on other stacks. The nearby QSVEnc report concerns AV1 ICQ and a lookahead setting on a different Windows system. Its 8.32 workaround did not establish a fix for this native HEVC test with lookahead absent. [QSVEnc issue #315](https://github.com/rigaya/QSVEnc/issues/315)

## Linux native resident-input sweep, T330 and T333

At 256 MiB, both 48-surface tests verified their preloads and yielded three decodable frames before SyncOperation status −17. Both 96-surface tests saw sharply longer upload/readback times after surface 64 and returned zero output before SyncOperation status −12. The earlier 48-surface sync failure and the 96-surface preload cliff are distinct observations. A successful preload alone cannot qualify an encode. Multiplying visible frame size by surface count cannot determine the amount that has to be mapped at once, since layout, alignment, internal allocations and memory placement also matter.

All 1,728 finite frames and 435,639 timed frames from the passing sizes had full software-decode and source-aligned PSNR records. The minimum was 45.24 dB. The timed early window was 0–5 s and late was 30–60 s. The passing tests went in ascending order within a boot. The change included aperture length, address, upstream coverage and Xe rebind. No descending comparison isolated those effects. A Windows allocation at 512 MiB cannot be inferred from the table.
